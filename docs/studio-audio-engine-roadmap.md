# NeaRer Studio low-latency audio engine

## Current implementation

### Offline multitrack Sound Desk

The Sound Desk supports up to eight audio layers per local project. Users can create, open, rename and delete up to 20 named projects; each project independently saves its track order, mute, volume, stereo pan, fade-in/fade-out, three-band low/mid/high EQ, room reverb, clip trim points and timeline start offset. The first launch migrates the former single-project preference into **My First Mix**. Project metadata is stored in a bounded, versioned local library; original imported/recorded audio files are never overwritten or deleted when a project is removed.

Each track has source trim-in and trim-out controls (for known-duration media) and a timeline start-position control bounded to 30 seconds. Clip preview uses the selected source range. The export composition applies the source clipping and represents a later start with a generated, bounded PCM silence lead-in before the trimmed source. The Sound Desk can generate a real amplitude waveform on demand by decoding the source through MediaExtractor + MediaCodec into a bounded 144-window peak representation; it does not retain the full decoded recording. Gold IN/OUT handles can be dragged horizontally over the waveform to adjust the clip range, while the numeric trim sliders remain available for precise edits. The minimum clip length is 500 ms (or the full duration for shorter sources). Waveforms are derived display data and are not persisted. Each named project now stores its own tempo (40–240 BPM), beat subdivision (quarter-, eighth- or sixteenth-note grid) and snap preference. The visible 30-second ruler marks bars, beats and subdivisions; when snap is enabled, moving a track start snaps to the nearest grid position, while users can turn snapping off for free placement. Version-1 project libraries migrate with the default 120 BPM and snapping off, preserving existing placement behavior. Timeline viewport navigation now provides 1×, 2× and 4× zoom with horizontal scrolling across the 30-second arrangement ruler; track-start markers are shown against the beat grid. The viewport is presentation/navigation state and does not alter saved track offsets. Tempo automation remains future work; beat snapping changes placement only and does not time-stretch audio. Unknown-duration sources do not expose trim controls.

The render path uses Media3 Transformer with parallel audio sequences and per-track PCM processors, then writes one AAC mix locally. Users can play the completed render in-app and share it. Clip preview plays the selected source range but is not a full effects preview; EQ, reverb, pan and fades are applied on export, and the rendered mix remains the authoritative effects preview. The render path is offline and does not upload audio. Media3 composition does not currently provide audio crossfading, so crossfades are not claimed.

### Vocal Pro offline editor

The separate Vocal Pro editor preserves the original take and exports a trimmed processed copy for A/B comparison. Its export chain runs key-aware monophonic pitch correction (when enabled) before the offline vocal-polish processor. The polish stage includes low-cut filtering, presence, de-essing, a noise gate, compression, air shelf, stereo width, soft saturation, room ambience and a linked output limiter. Custom vocal presets and manual controls are stored locally. This is an offline render path; the live pitch monitor is a separate input-monitoring tool and does not itself rewrite the recording. Failed or incomplete exports are deleted, and the app only exposes a completed output when a non-empty file exists.

### Live microphone monitoring

Studio has two live-monitor backends behind a Kotlin selection policy:

- **Oboe native duplex engine:** used on Android API 27+ for default input and selected USB input. The Kotlin layer selects an external headphone output and passes its ID to Oboe; the output builder pins that device and verifies `getDeviceId()` after opening. It refuses to start if Oboe opens a different output. After opening, the engine also verifies the actual input device ID and refuses to silently substitute another microphone. It opens a low-latency output stream first, then opens the input at the output stream's negotiated sample rate. It requests exclusive sharing and falls back to shared mode if exclusive is unavailable.
- **Java compatibility backend:** the existing AudioRecord/AudioTrack path remains available when native startup fails, on Android API 26, and when explicit USB device routing is not supported by the native API level. For an explicitly selected USB input, it checks Android's active routed-device ID after recording starts; if the actual route does not match the selection, it stops/releases the recorder and reports the route failure rather than silently claiming the wrong microphone. For microphone playback, it selects a wired, USB or Bluetooth headphone-class output, including BLE headsets, sets AudioTrack's preferred device, and waits for `getRoutedDevice()` to confirm the actual active output before writing any microphone samples. Android reports generic USB-device, Bluetooth-A2DP and Bluetooth-SCO output classes that may be speakers as well as headphones; the app now requires an explicit user confirmation for those ambiguous classes and warns that the device must be headphones. BLE speakers are excluded. If Android cannot activate the selected output, the monitor aborts and releases capture rather than sending live microphone audio to the phone speaker.

The Oboe callback path uses separate single-producer/single-consumer float PCM rings for output monitoring and Kotlin pitch analysis. The input callback copies samples into the rings; the output callback drains the playback ring and fills any missing frames with silence. The playback consumer discards stale queued frames above four output bursts, and the pitch-analysis consumer discards stale analysis frames above a bounded queue depth, preventing old audio from accumulating into hundreds of milliseconds of perceived delay. The engine starts input before output to avoid avoidable startup underruns. Callback code performs no file/network I/O, memory allocation, sleeping, or mutex locking. Pitch estimation remains outside the real-time callback on the Kotlin coroutine.

The native diagnostics report the negotiated sample rate, output burst and buffer size, actual low-latency and exclusive-sharing grants, actual input/output device IDs, Oboe xrun count when available, callback-level output underruns, capture-ring drops, stale-playback drops, stale-analysis drops and disconnection state. The UI must not interpret buffer duration as measured round-trip latency.

### Pitch-preserving time-stretch investigation

The app previously used Media3 1.5.1, whose default speed processor couples speed and pitch. Media3 1.11.1 adds `EditedMediaItem.Builder.setSpeed(SpeedParameters)`; the `shouldMaintainPitch` flag is passed through to the Transformer's `SpeedChangingAudioProcessor`, which leaves Sonic pitch at 1.0 while adjusting speed. Media3 1.11.1 requires compileSdk 36, so the isolated upgrade also moves the Android Gradle Plugin to 8.10.1 and CI Gradle to 8.11.1. The app's `targetSdk` remains 35 and `minSdk` remains 26; compile SDK and target SDK are deliberately kept separate. The next implementation step is to configure a constant speed curve with pitch preservation, verify that it is not combined with any separate speed-changing effect, and test output duration, pitch stability, clipping, and composition alignment. Until those tests pass, no pitch-preserving tempo adjustment is claimed. After the dependency upgrade, retain the API 26 minimum-install target and include a real-device smoke test on the oldest supported Android version; compileSdk 36 must not be mistaken for a new minimum OS requirement.

## Android and Oboe compatibility

- The app minimum SDK is 26. Oboe supports older Android versions, but this integration deliberately uses the native path from API 27 (AAudio) and preserves Java fallback on API 26.
- Oboe uses AAudio on Android API 27+ when recommended. The selected Android input-device ID is passed to Oboe; the opened stream's actual device ID is checked against the requested ID. If Android/Oboe cannot honour it, native startup fails safely and the existing Java path tries Android's preferred-device routing.
- Oboe 1.11.0 is consumed as a Google Maven Prefab dependency. The app enables Prefab, CMake, NDK 27.2.12479018 and packages arm64-v8a, armeabi-v7a and x86_64.
- The engine requests Float mono streams, enables Oboe's medium-quality sample-rate converter where needed, and uses the output stream's actual negotiated sample rate for input and pitch detection. The package name is explicitly attributed on both streams for modern Android capture permission checks. When Android reports unprocessed-input support, the native stream requests Oboe's Unprocessed input preset on API 28+; API 27 uses the supported VoiceRecognition preset, and the UI labels this accurately. The Java compatibility path can request Android's unprocessed source where supported. Actual stream properties are queried after opening; requested low-latency/exclusive modes are not treated as guaranteed.

## Lifecycle and recovery

A route disconnect triggers Oboe's error callback and marks the engine disconnected. Oboe automatically stops and closes the disconnected stream before `onErrorAfterClose`; cleanup checks both the callback's disconnect flag and the current stream state. It skips already-disconnected/closed streams, requests stop only for active/transitional-start states, and closes an opened-but-not-started stream without an invalid `requestStop()` call. It only stops/closes the still-open peer stream, outside the real-time callback. The Kotlin control coroutine then makes one bounded native reopen attempt when a headphone output is still present. If native restart fails, it falls back to the Java compatibility path. A selected USB input is re-verified by device ID on every native open. USB input removal is also observed by the parent recorder's Android device callback, which updates the selected input and restarts the monitor with the new selection.

The monitor observes headphone add/remove events while it is open and restarts against the newly selected output ID when the user changes accessories. The native path verifies the selected output ID at stream-open time and checks it in diagnostics; the Java path registers an AudioRouting listener, pauses the AudioTrack if Android changes the active route away from the selected headphone, and polls `routedDevice` before and after every microphone-buffer write so a delayed main-thread routing callback cannot continue forwarding audio to a changed route. The monitor refuses to start mic-to-output playback without a verified external headphone route and stops capture when that route disappears or changes, preventing silent fallback to the phone speaker. This is a device-routing check, not a guarantee that every connected accessory is physically worn or acoustically isolated.

On API 30+, the native builder explicitly requests Android's privacy-sensitive mode when Oboe opens an AAudio input stream; Kotlin gates the flag by runtime API level because Android 11 added the underlying AAudio capability. Oboe documents this setting as AAudio-input-only, so it must not be described as a guarantee if Oboe selects a different backend. On API 27–29 the native path cannot explicitly set the flag; the default VoiceRecognition preset is privacy-sensitive, while the optional Unprocessed preset is not guaranteed to be. The Java AudioRecord path separately requests Android's privacy-sensitive mode on API 30+. Microphone capture still starts only after the user's explicit in-screen opt-in and the pitch monitor never saves microphone audio.

## Validation still required

The code is integrated into the Android build. Automated checks compile the NDK target, run JVM tests (including PCM frame assembly, signal-level vocal processors and offline track DSP tests), and build/upload the debug APK. This does not prove physical-device performance. In addition to the microphone-monitor checks below, listen to a rendered multitrack mix with voice, music and effects on phone speakers, wired headphones and Bluetooth; compare the output against the source tracks and verify EQ/reverb tails, trim boundaries, track offsets, fades and pan placement. Required device testing includes:

1. Phone built-in microphone and speaker/headphones.
2. USB microphone plus wired/USB headphones on Android API 27+; verify both displayed input and output device IDs match the selected devices. Also verify no microphone samples are played until the output route has been confirmed.
3. USB microphone and headphone disconnect/reconnect while monitoring; verify output playback pauses immediately on route loss and does not fall back to the built-in speaker. Test BLE headset recognition, BLE speaker rejection, and the confirmation prompt for generic USB/A2DP outputs.
4. Screen lock/unlock and app background/foreground.
5. Competing microphone apps and microphone permission revocation.
6. At least one older Android device and one newer device.
7. Acoustic or electrical loopback measurements for round-trip latency and glitch rate.
8. Create, reopen, rename and delete projects; verify independent track settings and confirm source audio files remain intact. Include an immediate rename followed by app restart.
9. Generate waveforms for short, long, mono, stereo, silent and unsupported audio sources. Drag both waveform trim handles to the minimum, maximum and middle positions; verify the numeric sliders stay in sync.
10. Change project BPM and quarter/eighth/sixteenth-note grid, toggle snapping, place tracks near grid boundaries and confirm saved settings survive project switching and app restart. Confirm legacy projects retain their original free-placement behavior.
11. Switch timeline viewport between 1×, 2× and 4×, scroll to the end and back, and verify track-start markers remain aligned with the 30-second ruler without changing stored offsets.
12. Export mixes with different trim ranges and timeline offsets; listen for correct start/end boundaries and absence of unwanted silence or truncation. Test Vocal Pro success and failure paths and confirm failed exports leave no partial output files.

Do not publish a millisecond latency claim until those measurements exist. Bluetooth output can add substantial latency even when the input and processing path are native.
